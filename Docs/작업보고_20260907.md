## 1. 오늘 마지막 두 확인 건

### 1-1. 3층 출고 갯수 제한 — 코드에 있고, 실제로는 발동하지 않는다

기억하신 대로다. 다만 "없어진 것"이 아니라 **조건이 성립하지 않아 안 걸리는 것**이다.

3층에 있는 제한은 **202 피킹대 쏠림 제한** 하나다. 레거시 ECS 의
`Config m_nLimitStn202Picking2` 를 그대로 옮긴 것이다.

| | |
|---|---|
| 코드 | `cThread_SCH_3F.CV_RET_JOB` (`Count202Picking` + `GsGetLimitStn202Picking`) |
| 설정 | `ENV_IOSCH.INI [3F_RET] LIMIT_STN202_PICKING` |
| 판정 | `DEST_POS = 202` 이고 `201/203 에 피킹 대기 > 0` 이고 `진행중 202 >= 한도` 면 건너뛴다 |

발동하지 않는 이유는 둘이다.

1. **INI 에 `[3F_RET]` 섹션이 없다.** 그래서 한도는 기본값 `0` 이다.
2. **이 현장은 피킹출고를 쓰지 않는다.** `JOB_MST_HIS` 14,738 건을 훑어 보면
   작업구분은 1 / 2 / 4 / 6 / 11 / 12 / 14 뿐이고 **피킹(3) 과 반자동 피킹(13) 은 0 건**이다.
   `201/203 에 피킹 대기` 가 생길 수 없으므로 판정문의 두 번째 조건이 늘 거짓이다.

> **주의할 점** — 기본값 `0` 은 "제한 없음" 이 아니다. `진행중 202 >= 0` 은 늘 참이라,
> 훗날 피킹 작업을 쓰기 시작하면 **201/203 에 대기가 하나라도 있는 동안 202 출고가 통째로 막힌다.**
> 피킹을 도입할 때 `[3F_RET] LIMIT_STN202_PICKING` 을 반드시 정해 넣어야 한다.
> (레거시 ECS 도 기본값이 0 이었고, 현장에서 값을 넣어 쓰던 항목이다)

참고로 **1층 유량 제한은 살아 있다.** `DEL_HIS_SETTING(TABLE_NAME='1f_ret_rimit')` 의
`CYCLE = 20` 이고, CV 2호기/5호기의 `EQP_MST.CV_RET_CNT` 합이 이 값을 넘으면
대기대에서 새로 내보내지 않는다. 3층·BOX 에는 이런 유량 제한이 없다.

### 1-2. P/M(팔렛트 매거진) 입고 요청 — 적용되어 있지 않았다. 고쳐서 태웠다

`P/M` 은 예방보전이 아니라 **팔렛트 매거진**이다. 빈 파렛트를 상위에 요청하는 기능이다.

**있었던 상태**

`cThread_SCH_3F` 에 `CHECK_PM_STO_REQUEST` 함수가 있었지만 호출이 주석으로 막혀 있었다.
풀어 봐도 돌 수 없는 상태였다.

```
SELECT  CD.MC_NO, CD.PLC_NO, CD.STN_N        <- 그런 칸이 없다
   AND  IRM.STN_NO = CD.STN_NO               <- CV_DATA 에 STN_NO 가 없다
```

CV_DATA 에서 상위 스테이션 번호는 `HOST_STN_NO` 다(트랙 301 = 스테이션 207).
없는 칸을 짚어 질의 단계에서 끝났다. 이어지는 코드도 `JOB_TYP` / `PRODUCT_SIZE` /
`TRAY_LEV` / `TURN` / `LUGG_NO` 를 결과에서 꺼내는데 `SELECT` 에 없다.
질의를 고쳐 돌더라도 거기서 예외가 났을 것이다.

**고친 것**

- `CD.STN_N` / `CD.STN_NO` → `CD.HOST_STN_NO`
- 조회하지 않은 칸을 읽던 줄을 걷어냈다. 요청에 필요한 것은 스테이션 번호 하나뿐이다.
  번호가 비어 있으면 요청하지 않고 알린다.
- `RunSchFunc(CHECK_PM_STO_REQUEST)` 호출을 다시 태웠다.

**동작 구조**

```
트랙 301(P/M 입고대)에 빈 파렛트 + 출발 준비
   └ IF_REQ_MST 에 그 스테이션(207) 요청 슬롯이 있고 IF_STATUS <> 'N'  (직전 요청이 처리됨)
        └ UPDATE_IF_REQ_MST
             1) 슬롯을 IF_REQ_MST_HIS 로 옮긴다
             2) IF_STATUS 를 'N'(미처리) 으로 되돌려 상위가 가져가게 한다
```

**확인한 것**

- 고친 질의를 DB 에 그대로 던져 정상 수행. (전에는 없는 칸으로 오류)
- 3층 스레드를 켜고 IO_TASK 를 돌렸다. 매 주기 이 함수를 지나며 SQL 오류 없음.
- 쓰기 쪽은 `UPDATE_IF_REQ_MST` 의 두 단계를 같은 SQL 로 실행해 확인.
  슬롯이 이력으로 옮겨지고 `IF_STATUS` 가 `Y → N` 으로 바뀐다.

**확인하지 못한 것 — 남은 일**

- **실제 발동**은 트랙 301 에 빈 파렛트가 놓이고 `STO_READY` 가 서야 한다.
  CvSim 에서 화물을 놓아야 하는 부분이라 이번에 못 했다.
- **`IF_REQ_MST` 를 읽어 가는 상위 시스템이 이 구성에 없다.**
  저장소 안에서 이 테이블을 건드리는 것은 IO_TASK 뿐이고, 테이블은 비어 있다.
  WCS 쪽 절반까지가 이번 확인 범위다.
- 요청 슬롯 행은 **현장 기준정보**다. 스테이션 207 에 대한 `IF_REQ_MST` 행이 없으면
  기능이 조용히 안 걸린다. 시험용으로 넣었던 행은 지웠다.

## 3. 되짚어 볼 만한 것

### 3-1. 같은 정의를 두 저장소가 각자 복사해 쓴다

오늘 가장 크게 시간을 쓴 자리다. `DeviceMap??.xml` 은 CvSim(쓰는 쪽)과 CV_TASK(읽는 쪽)가
같은 정의를 각자 복사해 쓴다. 한쪽만 고치면 **조용히** 어긋나고, 어긋난 자리는 읽지 않는
비트가 되어 DB 에 값이 아예 안 들어온다(NULL). 눈에 안 띈다.

실제로 이 때문에 출고 대기대의 `RET_READY_RD` 가 늘 NULL 이었고 **출고 루프가 통째로
멈춰 있었다.** 화물이 대기대까지 와서 더 가지 않던 것이 이것이다.

세 겹으로 막아 두었다.

1. **정의를 맞췄다** — 여덟 벌을 CvSim 원본 기준으로 동기화
2. **읽는 쪽이 순서에 둔감해졌다** — 한 트랙이 여러 비트에 걸리면 OR
3. **기동할 때 대조한다** — `INI [DEVICEMAP] REF_PATH` 와 MD5 비교,
   다르면 화면과 `bin\Debug\DeviceMap_MISMATCH_{plc}.txt` 로 알린다. 맞으면 파일이 저절로 사라진다

### 3-2. 고친 사본과 안 고친 사본을 합칠 때 방향

`D551` 의 중복 세 줄은 **이미 한 번 진단하고 지웠던 것**인데 되살아나 있었다.

```
8ea03da   CvSim/DeviceMap02.xml 에서 세 줄 삭제              (고침)
7d76d69   Bin/Debug 산출물을 저장소에 넣음 — 고치기 전 파일   (오염본 유입)
7d77347   "Bin/Debug 와 CvSim 을 합쳐 여덟 벌 다 같게"       (오염본이 CvSim 으로)
4ae5941   Revert — CvSim 만 되돌아가고 Bin/Debug 는 그대로
288c98c   "CvSim 폴더를 Bin/Debug 와 똑같이 맞춘다"          (다시 오염)
```

"둘을 같게 맞춘다" 를 할 때 **어느 쪽이 옳은지 먼저 정하고** 하는 것이 좋겠다.

### 3-3. 조용한 폴백

HostSim 이 `Logic.xml` 을 못 읽으면 아무 말 없이 `HostSim.ini` 의 옛 `[LOGIC_GROUPnn]`
정의로 내려갔다. 그 정의는 아무도 손대지 않아 현장과 어긋나 있었고, 그래서
"102 → 105 로 지시하는데 중간 경유가 없다" 는 증상이 났다.
파일은 있는데 쓸 그룹이 하나도 없으면 이제 알린다.

### 3-4. 남은 것

- **`WCS_TASK_CV_1F_20260731_Morning`** 은 그날 상태를 남긴 스냅샷이라 `D551` 중복을
  일부러 두었다. 여기서 복사해 쓰면 같은 일이 난다.
- **`EcsDefine.xml` / `EcsLayout.xml`** 도 CvSim 과 HostSim 이 같은 이름으로 갖고 있다.
  한 폴더에서 돌리면 `Logic.xml` 과 같은 충돌이 날 자리다. 이번엔 손대지 않았다.
- **랙투랙(4 / 14)** 은 스케줄러가 다루는 자리가 없다. 정상도 반자동도 처리되지 않는다.
  원래 그랬던 것이라 새로 만들지 않았다.
- **HostSim 종료 버튼**이 물고 있던 작업을 ECS 에 취소하지 않아 고아 작업이 남는다.
  재시도 3회 상한으로 폭주는 막았지만, 취소 전문 규격이 있는지 확인이 필요하다.

## 4. 마지막 상태

전 구간이 돈다. `이동 → 입고 → 출고 → 완료 → 이동` 이 끊김 없이 반복되는 것을 확인했다.

```
14:33:47  O6A1043  이동 101 → 107
14:38:27  F6A104331107   이동 완료(도착 107)        → 삭제
14:38:29  O1A1044  입고 107 → SC905 / 09-001-01
14:40:00  F1A104411107   입고 완료                  → 삭제
14:40:01  O2A1045  출고 09-001-01 → 105
14:41:26  F2A104521103   출고 완료(도착 출고대 103)  → 삭제
14:41:27  O6A1046  다음 사이클
```

출고 목적지도 확인했다. 출발지가 `000` 인 조건(예전에 `0 + 150 = 150` 이 나오던 자리)에서
SC 905 의 대기대 259 → **스테이션 155** 가 정확히 지시됐다.

시스템은 이 보고서를 쓰면서 모두 내렸다.
